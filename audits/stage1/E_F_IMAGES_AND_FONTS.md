## PART E — IMAGE / ASSET FLOW

### E.0 Verdict (headline)

**An image is NEVER a real item in the content stream.** The input format (`dfa-lexer` → `block-tokenizer`) has no image token — tokens are only `heading | paragraph | endnote | endnote-class | editorial` (parser/block-tokenizer.js:41-129). Images exist exclusively as a **decoration side-channel**: ornament rects (`page.decorations[]`), shaar gate backgrounds (`planDecorations` slots), and fixed-position custom-page images (`page.custom.images[]`). An image **cannot** appear inline inside a paragraph or note today; DOCX embedded pictures are dropped silently on import (see E.6).

- parser/block-tokenizer.js:41-129 — token types enumerated; no image/media token.

### E.4 Same asset identity DOM vs PDF?

- **SVG ornaments:** YES — single ink source `ornament-ink.js` consumed by dom-renderer (background data-URI), geometry-projector (vector paint) and pdf-writer (pdfOps) — EXT-4 "single ink source" (ornament-ink.js:1-13; geometry-projector.js:289-315; pdf-writer.js:458-465).
- **Raster/`image` ornaments & shaar backgrounds & custom-page images:** NO — DOM renders them (dom-renderer.js:483-489, 533-545, 597-604); PDF draws nothing (pdf-writer.js:460 comment; projectPage has no custom-page branch).
- Dimensions: DOM uses registry `box`/settings; PDF ornaments use the same rect (F-09 single source — ornament-plan.js:318-326, ornament-fit.js:160-168).

### E.5 Where images are stored

- SVG: `asset-registry.collections` — as sanitized **SVG text + percent-encoded dataUri** (asset-registry.js:48-54). Never stored as bytes.
- Fonts (for contrast): raw ArrayBuffer in `appliedFontsReady` cache + base64 in `bytesB64` (imud-library.js:111-119) + Worker `registeredFonts` (measure-api.js:22, 28-43).
- Raster: only inside extension JSON strings (`settings._customPages` → custom page `images[].src` data-URIs) — never decoded.

### E.6 IMAGE LOSS POINTS (ranked)

1. **DOCX import drops all embedded images** — docx-import.js reads only text/footnote refs; `word/media/*` ignored, zero warning. (L-critical, content loss)
2. **Raster images are not drawn in exported PDF** — pdf-writer.js:458-465 draws only `pdfOps`; `inkType:'image'` yields none (geometry-projector.js:297). Custom-page images/boxes not projected either. DOM shows them → PDF doesn't. (L-critical, fidelity)
3. **Extensions bundle top-level `images[]` never wired to the engine** — app-shell.js:225-243 `onBundleChange` maps only `bundle.styles → settings._customStyles` and `bundle.pages → settings._customPages`; `bundle.images` is validated (style-schema.js:253-290, incl. `alt` field!) and round-tripped by extensions-io, but **no consumer renders it** (grep: only extensions-io/extensions-panel/display + export). The `alt` text is therefore dead metadata — an a11y/image-intent channel with no sink. (L-critical, dead feature)
4. **Folder/manifest asset import is dead code** — `importAssetFolder`/`wrapShaarMedia`/`groupThemeSets`/`activateThemeSet` have production callers nowhere (tests only). REQ-ORN-07 unreachable by users. (L-high)
5. **No raster dimension measurement** — natural size is declared (mm) or defaulted (shaar box 40/40/30/30), never sniffed from PNG/JPEG headers; `backgroundSize:100% 100%` (dom-renderer.js:487, html-export.js:133) stretches to declared rect. (L-high, distortion)
6. **No format sniffing** — extension-based acceptance (assets-import.js:17-26) + data-URI prefix test (45); a `.png` containing garbage or a mislabeled JPEG passes and renders as broken background. (L-medium)
7. **`media:null` path** — wrapShaarMedia sets `media:null` for binary content with comment that "UI will attach blob" (assets-import.js:44-49) — no such UI code exists. (L-medium, dead path; same as #4)
8. **Missing dimensions on ornaments** — ornament ink natural size is em-heuristic; shaar title box falls back to hardcoded margins when neither design `box` nor `shaar-main-box` present (dom-renderer.js:559-562). (L-medium)
9. **No alt text anywhere in rendering** — images become CSS `background-image` divs (dom-renderer.js:486, 554, 602) — invisible to assistive tech; the only `alt` field in the system (extensions images) is never rendered. (L-medium, a11y)
10. **Custom-page image `src` unvalidated for offline** — custom-pages.js:67 accepts any string (external URL ok), while extensions images force data: (style-schema.js:274-281); an external URL breaks the offline-guard HTML export (html-export.js:9-32) or silently fails in PDF (nothing drawn anyway). (L-medium)
11. **Silent re-registration** — same collection+id replaces prior asset without notice (asset-registry.js:9, 40-41); acceptable for library updates but can swap ink under an existing document without trace. (L-low)
12. **Worker/registry divergence** — UI and Worker registries are independent maps kept in sync only by explicit dual `registerAssets` calls (imud-library.js:242-247); a failed worker registration is swallowed (`catch { /* Worker will report */ }`) → DOM shows design, PDF lacks it. (L-low/medium)
13. **ZIP entry denials under-reported in DOCX path** — `zip.denied` voided (docx-import.js:192-195). (L-low)

## PART F — FONT-RANGE HANDLING

### F.0 Verdict (headline)

**There is no font-range syntax in the input format at all.** Fonts are chosen per *structural context* (body / heading level / note channel / shaar block / first-word), not per text range: settings keys like `heading-N-font`, `first-word-font`, `f-note-body-font`, `s-note-body-font`, `page-num-font`, `shaar-*-font`, `heading-0-body-font` (core/settings-registry.js:55-159). The word is the atomic unit end-to-end; **family identity is preserved per word (via `fontKey`) through measurement → line-break → page-plan → projection → PDF**, but **a single word can never carry more than one family** — there is no sub-word font segmentation anywhere. The only intra-word variation is *size* (paren scale, custom-style factor, window word 1.5×) and per-*character* glyph fallback in the PDF writer (missing-glyph → /F1 → /F4), which is a font-fallback mechanism, not a user font range.

### F.2 "MULTI-FONT WORD TRACE" — full chain

**Premise:** the input format cannot mark fonts inside text (F.1 #1). The closest real scenario — a *word* that must render in a different family than its neighbors — exists in exactly four engine-supported forms:

(a) **Window word** (legacy IMUD profile only) — `first-word-font` (FrankReal).
(b) **Heading word** — whole heading line in `heading-N-font`.
(c) **Note-channel word** — footnote/side-note words in `f-note-body-font`/`s-note-body-font`.
(d) **Registered-family word** — shaar blocks/folio/header slots in `shaar-*-font`, `page-num-font`, `hdr-*` slot fonts.

Trace for each stage (with what a hypothetical multi-font word would suffer):

1. **Parser output** — word = substring of paragraph text split on whitespace (pipeline.js:467-481). No attributes possible. *A multi-font word would be flattened to an unattributed string here — the format has no carrier.* Evidence: block-tokenizer tokens `{type, parts:[{kind:'text'|'note-ref'}]}` (126).
2. **Measurement** — `MeasureAPI.measureTextWidth(text, sizePt)` (measure-api.js:142-162) uses ONE profile (`this.fontProfile` = body). Headings re-measure via `widthFor(text, hSize, hFont)` → `MeasureAPI.forFamily(hFont)` real metrics else approximation (pipeline.js:205-219). `measureWithParen` scales width only (515-527). *Whole word measured in a single family; segments would each need separate measure calls that don't exist.*
3. **kp-linebreak** — boxes `{text, width}` (kp-linebreak.js:41); words re-emerge as plain strings with NBSP re-glue (160-171). No font data.
4. **Line model** — `ln.words: string[]` + line-level kind/level (pipeline.js:324, 529-547). Only *word-index* attributes exist: `parenSpans`, `customSpans` (size semantics).
5. **Page planning** — dp-planner/column-flow/retreat move line objects verbatim; no font fields touched.
6. **geometry-projector** — `projectLine` emits `wordPos {text,x,w,sizePt?,fontKey?,color?}` (geometry-projector.js:730-736). `fontKey` is assigned **uniformly to all words of a heading line** (733) or per note-channel via `wrapNoteTokens` (377). Legacy: `placeWords` + explicit `fontKey:'window'` per window word (legacy-projector.js:329-333) and `fontKeyOf(hFam)` per heading words (306-309).
7. **dom-renderer** — `renderLine` sets `el.style.fontFamily = fontStack(lineFontFamily(ln))` **on the line element** (dom-renderer.js:117-118); per-word spans only for paren/custom size (165-183); `.w--window` class only in the legacy branch (959-976). *In the DP path, per-word family is expressed only through CSS inheritance from the line.*
8. **pdf-writer** — `emitWord(w.text, x, y, w.sizePt||ln.sizePt, w.fontKey, w.color)` (409) → /F1..F6 or /F7+ family subset (348-354); per-char fallback runs F1→F4 (364-376). **Family identity per word is preserved to the last mile** — the run-loop even switches `/Fn size Tf <hex> Tj` per run inside one BT/ET (392-402).
9. **html-export** — same DOM as live (export-api.js:55-78) + embedded @font-face CSS (imud-library.exportFontCss). Per-line inline fontFamily + `.w--window` CSS class survive.

**Verdict:** family identity IS preserved end-to-end **at word granularity** (hard evidence: `w.fontKey` consumed in pdf-writer.js:348-354 and export-api.js:389-396 word-collection per fontKey). It is **NOT preserved (nor expressible) below word granularity**: there is no parser syntax, no line-model field, no renderer API for intra-word font segments. A "word with multiple font segments" is flattened to a single string at step 1 and would render entirely in the line's/context's single family. The only intra-word font change the engine performs is the PDF missing-glyph fallback (F-word → F1 → F4), which is glyph-availability-driven, not semantic.

### F.3 Known asymmetries / risks (font)

1. **DP-path first-word decoration is dead** — `applyDropWord` computes `block.firstWord` (pipeline.js:580-581, dropword.js:69) but no DP renderer consumes it (`dropWordCssClasses` has zero callers; grep `firstWord` in output/ → legacy only). Legacy profile implements it fully (legacy-imud-flow.js:617-693 → legacy-projector.js:310-355 → /F2). **Same setting, two engines, one output.**
2. **WOFF2 families: DOM yes, measurement approximated, PDF no** — imud-library.js:128-136 skips worker registration for `.woff2`; `familyFontKeyOf` (geometry-projector.js:37-46) then returns null → F1; heading measured with `0.6em/char` floor (pipeline.js:217-218). Display≠export drift class EXT-13, inherent to the 1315-family extended catalog (D-87).
3. **Unregistered families silently flatten in PDF** — word keeps `fontKey=null` → F1 (pdf-writer.js:353-354), while DOM shows the real family via @font-face; `fontStatus` classifies 'unknown' but nothing blocks the choice (imud-library.js:96-100).
4. **Line-level font in DOM vs word-level fontKey in PDF** — DOM heading font comes from `lineFontFamily(ln)` (line-font.js:30-37) which reads `heading-N-font` **at render time**; PDF fontKey is fixed at projection (geometry-projector.js:682). Both read the same settings, but a settings change between typeset and export (light vs heavy classification) could theoretically diverge — mitigated by heavy-class ⚡ gating (retypeset-policy.js).
5. **`heading-0-size-pt`** — H0 ("הקדמה"/"כותרת 0") flows the generic `heading-${level}-size-pt` path (pipeline.js:312); the separate `heading-0-body-font` exists for the preface *body* only in the legacy profile (legacy-imud-flow.js:2351-2352) — in the DP profile a preface body paragraph uses plain `body-font`.
6. **Per-word `sizePt` (paren/custom/window) is preserved** through projection (geometry-projector.js:726-736, S68 R2-M6) — proof that per-word attributes CAN travel the whole chain; adding per-word `fontKey` for body words would follow the identical channel.

### F.4 Font assets map

- `ui/assets/imud/imud-fonts.json` — priority catalog (~443 TTF families), loaded by imud-library.loadFontCatalog (50-81).
- `ui/assets/imud/fonts-extended.json` — 1315 families (WOFF2), merged into `byFamily` (62-72); actual `.woff2` files in `ui/assets/imud/fonts/` (98MB, present in repo — see LS listing).
- `ui/assets/imud/fonts/*.ttf` — 62MB priority fonts; registered to Worker for real measurement + PDF embedding.
- Resolution chain DOM: family → `byFamily` → fetch file → `FontFace` (imud-library.js:138-145).
- Resolution chain Worker: family → `registerFont(name, bytes)` → `registeredFonts` (measure-api.js:22-43) → `MeasureAPI.forFamily` (220-229) / `familyFontKeyOf` (geometry-projector.js:37-46).
- Resolution chain PDF: fontKey → fixed slots F1(body)/F2(window)/F3(heading)/F4(FRL fallback)/F5(fnbody)/F6(margin) + `extraFonts` F7+ (export-api.js:374-435; pdf-writer.js:272-287, 348-354); each slot = CIDFontType2 + FontFile2 subset + ToUnicode (pdf-writer.js:505-515, font-subset.js:39+).
- HTML: `exportFontCss()` @font-face data-URIs from `bytesB64` (imud-library.js:401-408) injected via `meta.fontCss` (html-export.js:169-176).

## Cross-cutting observations for the unification project

1. The **word-level attribute channel (`sizePt`/`fontKey`/`color` on projected words)** is the proven carrier that already survives parser→measure→KP→DP→projector→PDF. Any future inline-image or per-segment-font feature should ride this channel (words would need to become objects or carry sentinel-prefixed segments like PAREN_SENTINEL today — pipeline.js:478-480, 536-547 shows the sentinel pattern works for size).
2. The **sentinel pattern** (`PAREN_SENTINEL`, `CUSTOM_SENTINEL+styleId`, `MARK_TAG` \uE102, `ATOMIC` \uE000) is the existing mechanism for sub-word attributes that survive line breaking — but it encodes *size/style-id*, never family.
3. **display≠export** is a first-class tracked failure class in this codebase (EXT-13, S71.1, D-86); raster images in PDF (E.6 #2) and WOFF2 families in PDF (F.3 #2) are the two remaining structural instances of exactly this class.
4. Dead/duplicated subsystems found: assets-import folder pipeline + theme-sets activation (test-only), extensions top-level images (validated, never rendered), dropword DP metadata (computed, never rendered).
