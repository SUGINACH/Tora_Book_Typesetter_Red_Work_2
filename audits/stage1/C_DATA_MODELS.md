# Stage 1 — C. Data-Model Map of the Engine (branch `audit/stage1-engine-state-20261115`)

Scope: `red-build/src/engine/**`. Every claim cites `file:line`. `pipeline.js` = `red-build/src/engine/core/pipeline.js`, `legacy.js` = `red-build/src/engine/layout/legacy-imud-flow.js`, `dp` = `red-build/src/engine/layout/dp-planner.js`, `geo` = `red-build/src/engine/output/geometry-projector.js`, `dom` = `red-build/src/engine/output/dom-renderer.js`.

**Two engines share one repo.** `typeset()` dispatches: if `settings['_layout-profile']==='imud' && settings._imudRaw` → `legacyTypeset()` (pipeline.js:123-126). Everything downstream of parse is **duplicated per path** (tokenizers, line-breakers, page models, footnotes, TOC, projectors) with ad-hoc compatibility shims between them (see §Competing models).

Note on the terms in the task brief: there is **no model named `fragments` or `inlineRuns`** anywhere in the code (rg over `src/` returns nothing). The closest analogues are the paragraph-token `parts[]` (block-tokenizer.js:126) and the per-line `customSpans`/`parenSpans` arrays (pipeline.js:539-546). All richness is carried by **strings + PUA sentinels**, not by structured runs.

Sentinel alphabet (the "encoding layer" of the DP model):
- `U+E000` `ATOMIC` — atomic space inside a note (block-tokenizer.js:8, pipeline.js:47)
- `U+E101` `PAREN_SENTINEL` — word is inside `(...)` scale (pipeline.js:46)
- `U+E102` `MARK_TAG` — note-marker tag glued to anchor word (markers.js:186, pipeline.js:235-239)
- `U+E103/U+E104` `CUSTOM_SENTINEL/CUSTOM_SEP` — word belongs to custom inline style `<id>` (pipeline.js:50-52)
- `U+00A0` NBSP — glued unit boundary (protectors.js:10-16, kp-linebreak.js:33)

## 2. Specific questions, with evidence

### 2.1 Where does the parser produce words/tokens? What fields does each word carry?

- **Tokens, not words, are the parser product.** `lexDocument` (dfa-lexer.js:57-87) → `{metadata, bodyLines}`; `tokenize(bodyLines, opts)` (block-tokenizer.js:41-129) → tokens. Exact shapes:
  - heading: `mkToken('heading', { level, text, raw })` block-tokenizer.js:68
  - endnote (numbered): `mkToken('endnote', { num, text, raw })` block-tokenizer.js:77; plain: block-tokenizer.js:84
  - endnote-class directive: `mkToken('endnote-class', { title, raw })` block-tokenizer.js:90
  - editorial: `mkToken('editorial', { text, removed: true })` block-tokenizer.js:96
  - paragraph: `mkToken('paragraph', { parts, notes, unmatchedClosers, raw })` block-tokenizer.js:126 where `parts = [{kind:'text', value} | {kind:'note-ref', noteIndex}]` (block-tokenizer.js:112-124) and `notes = string[]` with spaces replaced by `U+E000` (block-tokenizer.js:118).
- **Words are produced in the pipeline** by splitting `part.value` on whitespace: `for (const wordRaw of src.split(/\s+/))` pipeline.js:468, pushed as decorated strings pipeline.js:478-480. **A DP "word" is a bare `string`** — it carries *no* font, no marker, no source identity. All provenance rides on:
  - block-level fields: `tokenId`, `part`, `notes`, `noteAssignments`, `parenCharSpans`, `flatWordOffsets` (pipeline.js:569-574);
  - PUA sentinels inside the string (pipeline.js:478-479, 492);
  - line-level side arrays `ln.parenSpans:[wi]`, `ln.customSpans:[{wi,styleId}]` (pipeline.js:539-546).
- **Legacy words:** `splitWords` returns `{words (with U+E000 atomic), disp (marker-substituted display form), out (original words), notes, dispW}` legacy.js:451-520. Words are also bare strings; marker positions are recovered at emission by re-running `findNotes` over each word (legacy.js:1658).

### 2.2 How do font ranges flow into words? Is family preserved per fragment?

There are **no font ranges in the parser** (bracket-scanner handles *notes*, not fonts — bracket-scanner.js:1-2). Two "range" mechanisms exist, both applied **per whole word** in the DP path:

1. Paren scale: `parenSpansOfFlat(flatBody)` → `[{from,to}]` char spans pipeline.js:92-102; membership tested by word start offset only — `offsetInSpans(at, spans)` requires `at > s.from && at < s.to` pipeline.js:104-108; applied by prefixing the whole word with `U+E101` pipeline.js:479 and measuring `base * parenScale` pipeline.js:523-526.
2. Custom inline styles: `matchInlineStyles(flatBody, customStyles)` → ranges → `csInlineSpans [{from,to,styleId,factor}]` pipeline.js:417-424; membership = **word-range overlap** (`info.at < s.to && (info.at + wLen) > s.from`) pipeline.js:475-476; the entire word is wrapped `\uE103<styleId>\uE104word` pipeline.js:478 and measured at one size factor pipeline.js:517-522.

**After measurement and line breaking** the sentinels are stripped and re-expressed as word-index arrays `ln.parenSpans` / `ln.customSpans` pipeline.js:533-547; renderers re-derive per-word effective size in geometry (geo.js:690-701 `effSizeOf(i)` — one size per word) and DOM (dom.js:165-180 `span.w--paren` / `span.w--custom`). **Font family is never carried per word**: the family is a property of the *line* — heading lines via `heading-N-font` settings read in `projectLine` geo.js:682 and `renderLine` dom.js:117-118 (line-font.js:16-37), legacy lines via `ln.font` legacy.js:2352. 

**A word with multiple font segments is flattened:**
- DP: impossible to represent — one word ⇒ one sentinel ⇒ one scale (pipeline.js:475-480); a word half inside a paren span is either fully scaled (if its start offset is inside) or fully unscaled (if not) — the `at`-only test pipeline.js:106-107 means a word starting before `(` but ending inside gets **no** scaling, and one starting inside but ending after `)` is fully scaled.
- Legacy: *finer* granularity exists for measurement only — per-character paren segmentation inside a word legacy.js:579-597, and marker-adjacent words split into prefix/marker/suffix measured at different sizes legacy.js:501-514 — but the emitted line still stores whole words with boolean flags (`parenFlags/parenStarts/parenEnds`, legacy.js:1644-1695), so sub-word font boundaries do not survive to render except via the marker/paren boolean edges.

### 2.3 How do note markers flow through words → lines → pages?

**DP path:**
1. Parse: `[note]` text extracted by `scanBrackets`; paragraph gets `parts[].kind==='note-ref'` + `t.notes[]` (block-tokenizer.js:102-126).
2. Marker allocation at parse time: `markerFor(nextMarkerNum(...), markerStyle)` pipeline.js:485; recorded in `noteAssignments.push({noteIndex, marker})` pipeline.js:487 and `markersByToken.set(t.id, noteAssignments)` pipeline.js:508.
3. Body placement: footnotes/endnotes modes push the bare marker word pipeline.js:505 then `bindMarkersToNeighbors` glues it to its anchor as `anchor\u00A0\uE102marker` (or forward-glued `\uE102marker\u00A0next`) pipeline.js:226-247. Inline mode embeds the full placeholder `\uE102marker\uE000note-text-with-E000-spaces` pipeline.js:492-498.
4. Lines → pages: marker stays an opaque string inside `ln.words`; `pushLines` copies `{...ln, meta:{tokenId...}, seq}` dp.js:208.
5. Note body flows separately: `notes.push({text, marker, tokenId, noteIndex, part})` pipeline.js:503 → block → `reserveNotes` pushes `{...n, heightPx, mode, isContinuation}` into `page.footnotes` dp.js:269-286.

**Is marker→body linkage structural?** Partially. The *note side* is structural (`page.footnotes[].marker` matched against `block.noteAssignments[].marker` / `markersByToken`). The *body side* is **string reconstruction**: `countKnown(w)` identifies markers inside rendered words only by scanning for `MARK_TAG` (`U+E102`) or the first `U+E000` and then matching the fragment against a set of known marker strings pipeline.js:1041-1058 (design note D-53 at pipeline.js:1042-1043). `renumberPageScopedMarkers` rewrites markers by **regex over word strings** (`\uE102<old>(?=\u00A0|$)`, `^<old>\uE000`) markers.js:147-163. So after a marker is glued into a word, its identity survives only as text.

**Legacy path:** markers are generated at *emission* time — `emitLinesWithMarkers` re-finds notes in each word (`findNotes(w, fnOpen, fnClose)` legacy.js:1658), computes an occurrence ordinal `notesUpTo` legacy.js:1631-1640, keys the note as `` `${tok.id}#${ord}` `` legacy.js:1668, and calls `enqueueNote(n.text, undefined, noteKey)` which assigns/reuses a chapter number via `fnNoteNumbers` map keyed by that string (or falls back to text matching) legacy.js:1446-1474. The marker word is pushed into `words` and its index recorded in `markerIdx` legacy.js:1675-1676. Body-side linkage is therefore **entirely reconstructed by string/ordinal parsing** at line-emission time — the S6.0(F3) comment (legacy.js:1447-1456) documents that text-only dedup previously merged two distinct identical notes, i.e. content loss caused by this string-keyed model.

### 2.4 Shape of a line in kp-linebreak vs legacy-imud-flow vs dp-planner candidates

- **kp-linebreak (DP):** `{ words: string[], widthPx: number, heightPx: number, isLast: boolean }` kp-linebreak.js:181 (greedy fallback identical at :208). Plus pipeline stamps (§1 #6). No y — position is flow-stacked by the projector.
- **legacy-imud-flow:** `{ words, parenFlags, parenStarts, parenEnds, window, heightPx }` from `breakPara` legacy.js:672,691; emitted with `markerIdx` legacy.js:1695; final column line adds explicit `y, paraId, lineIdx, align, sizePt, font` legacy.js:3007-3023. Position is **pre-computed y** (absolute), not stacked.
- **dp-planner "candidates" are not lines** — they are split points `{cut, before, after, capacityBefore, capacityAfter, score}` candidate-generator.js:35; the line objects the DP pushes are the KP lines cloned with `meta`/`seq` dp.js:208.

These are **two competing line models** (stacked vs absolute; plain words vs annotated words) bridged only by renderer-specific code paths (`renderPage` vs `renderLegacyPage` in dom-renderer; `projectPage` vs legacy-projector).

### 2.5 Page/column model: legacy vs DP vs geometry-projector CP5

- **DP page** (dp.js:110-114 + mutations): `{index, type, template (from page-templates: width/height/columns[{x,w}]/gutter/contentBox/margins), columns:[[line],…], footnotes:[note], sideNotes:[rec], headingsOnPage:[], balanceInfo, fnReservedHeightPx, chapterOpening}` later `{spanning:{lines,heightPx,…}, pageNumber, folioDisplay, pageNumberDisplay, headerCtx, firstWord, lastWord, isRecto, opensWithHeadingLevel, header, _metadata, parenRanges, decorations, terminalResidual}` (pipeline.js:816-872, 1162; dp.js:526).
- **Legacy page** (legacy.js:1136-1156): `{index, type, legacy:true, pageNumber, folioDisplay, headerSlots, bands:[], columns:[[],[]], marginNotes:[], footnotes:[], sideNotes:[], fnSep, toc, _metadata, ascentEm, template:{synthesized from GEO constants}}` plus `gateLines` (legacy.js:1315-1316, 3081). Key differences: absolute-positioned `bands` and `gateLines` instead of `spanning`; `marginNotes` instead of placed `sideNotes`; synthesized two-column `template` from `GEO` legacy.js:1149-1154; `toc` rows on the page itself.
- **CP5 projected page** (geo.js:60-70): `{width, height, contentBox, columns, lines:[{x,y,w,h,words:[{text,x,w,sizePt?,fontKey?,color?}],align,kind,level,isLast,sizePt,tokenId,baselineY,ascentPx,descentPx,capPx}], footnotes, folio, header, spanning, decorations}` — a *flat, fully positioned* model: every word gets explicit `x/w` (geo.js:723-738); baselines filled by `attachBaselines` geo.js:752-774; endnote/side-note/TOC/shaar content all flattened into `out.lines` (geo.js:88-107, 478-562).

### 2.6 Where are images represented?

**Nowhere in the content stream.** rg over `engine/` for `image|png|jpg|asset` shows images only as:
- decoration rects with `d.image` refs resolved through `asset-registry.resolveAssetRef` (`imud:<collection>:<id>` → sanitized SVG data-URI) asset-registry.js:80-89; consumed at dom.js:482-516, geo.js:296-297, legacy-projector.js:707;
- settings-driven backgrounds/slots (`background-image`, `shaar-main-image` …) settings-registry.js:225-244; page-decorations.js:41-98;
- custom pages (PT-09) with placed images `{src (data: URI only), x, y, w, h}` custom-pages.js:55-67, 114-125;
- custom-style images in style-schema (`image-external-src` rejected) style-schema.js:261-284, rendered as `.custom-image` dom.js:599.

No word/line/page-column object has any image field; images are a **render-time side channel**, never laid out by the line breaker.

### 2.7 Where does content-preservation accounting happen, and what representation does it compare?

- **DP:** pipeline.js:894-1114.
  - Source side `srcWordsOf(t)` pipeline.js:928-958 — recomputes a word list from `tokens` (body parts + marker + note text per note-ref + custom-style markers via `customFootnoteMarkers`/`customEndnoteTokens`).
  - Output side `outWordsOfAll()` pipeline.js:961-996 — walks the **rendered model**: page lines (including spanning band), footnote gutter texts, endnote pages, side notes.
  - Comparison: **word multiset** — `norm = arr.slice().sort().join('\n')` equality pipeline.js:1010-1011, diff by per-word counts `mismatchDetail {kind:'multiset-mismatch', diff}` pipeline.js:1013-1019; plus per-token placement check pipeline.js:1023-1033; plus **marker count consistency** body-vs-assigned and display-vs-assigned pipeline.js:1036-1107 (identification by `MARK_TAG`/`U+E000` tags only, pipeline.js:1041-1058).
  - Failure → ledger `text-completeness` record pipeline.js:1111-1114.
- **Legacy:** legacy.js:3494-3589 (`contentStats`): source = metadata + token texts (+sideNote/endNote), normalized by stripping note delimiters legacy.js:3520-3538; output = column words + windowWords + footnotes + marginNotes + bands + gateLines (TOC/folio excluded) legacy.js:3557-3569; comparison is **one-directional ≥** (every source word covered) legacy.js:3570-3578; result exposed as `contentStats {sourceWords, outputWords, missing…}` legacy.js:3690.
- **Tests:** `contentPreserved === true` asserted in ~40 tests, e.g. canonical.test.js:37, long-real-text.test.js:44,77,90,127,140 (both paths), s75-notes-flow.test.js:78,133, s76-notes-flow.test.js:80,100,159,160, legacy-result-contract.test.js:65, imud-migration.test.js:117.
- Representation compared: **plain scrubbed word strings** (`scrubForCompare` pipeline.js:900-905 normalizes `U+00A0/U+E000/U+E101/U+E102`→space, FF9F/FF93→gershayim) — i.e. accounting is blind to font, style, order, and structure; it verifies only the word multiset.

## 3. INFORMATION LOSS POINTS (every reduction, with evidence)

1. **Paragraph structure → flat word strings** (DP). `t.parts` (text/note-ref alternation) is split to `allWords` strings; note-ref positions become marker strings pipeline.js:465-507. The word→part mapping is lost; only `noteAssignments` order and `flatWordOffsets` (pipeline.js:397-405, 572) preserve coarse anchors. *Partially reversible* via markers.
2. **Inline note body flattened into a word string.** Placeholder `\uE102marker\uE000text…` pipeline.js:492-498; extraction is string parsing (`explodePlaceholderWord` pipeline.js:908-917; `countKnown` pipeline.js:1041-1058). Note body loses all structure (already only a string since block-tokenizer.js:118).
3. **reject-to-body destroys the structural note.** `blk.notes.splice(ni,1)` + rewrite of the tagged word to `anchor\u00A0marker\uE000text` + `blk.rejectedNotes` bookkeeping dp.js:295-321 — after this the note exists only inside a body word string (accounting compensates at pipeline.js:974-1079).
4. **Marker identity survives as text only.** After gluing (pipeline.js:235-239), renumbering must regex-rewrite word strings markers.js:147-167; DOM/PDF identification is `w--fnmarker` by `markerSet` of *indices* in legacy (dom.js:1058) but by tag-scan in DP accounting (pipeline.js:1046-1058).
5. **Font family is line-level, not word-level** (both paths): pipeline.js:313/322 (heading font on block), line-font.js:16-37, dom.js:115-118, geo.js:676-683. A word that changed font mid-word cannot be represented; the DP custom-style/paren scaling is one-factor-per-word (pipeline.js:475-480, 517-526).
6. **Paren spans are word-granular by start offset** — `offsetInSpans` uses only the word start `at` pipeline.js:104-108 ⇒ words straddling a paren boundary are mis-scaled whole; contrast legacy which segments per character for *measurement* legacy.js:579-597 but still emits boolean flags per word legacy.js:1652-1695.
7. **Sentinels stripped at render (irreversible).** `scrubPUAText` removes PUA + NBSP→space at dom.js:47, 162 and geo.js:702; the CP5 projection (geo.js:740-748) is a terminal form — from it you cannot recover tokens, note structure, or styles (only `tokenId` survives per line).
8. **Legacy: note text removed from body line and replaced by marker word.** `emitLinesWithMarkers` splits a word into prefix/marker/suffix legacy.js:1661-1683; the note text lives only in `fnQueue`/`paraNotes` keyed by `token#ordinal` string legacy.js:1665-1673 (string-keyed — documented duplicate-merge bug, legacy.js:1447-1456).
9. **Legacy `disp` vs `out` duplication** (marker-substituted measurement words vs original words) legacy.js:485-519 — the display form is what the model measured; the original intra-word note delimiters are gone from `out` words only because `findNotes` re-derives them from the raw token text at emission (legacy.js:2146).
10. **`dh` (דיבור המתחיל) is dead data.** Detected and given font/color pipeline.js:380-387, stored on block (pipeline.js:571) — no renderer or planner reads `blk.dh` (rg over `src/`: only pipeline.js:386-387).
11. **`block.firstWord` (DP drop-word) is dead data.** `applyDropWord` sets `block.firstWord` dropword.js:69 and exports `dropWordCssClasses` dropword.js:78 — neither is consumed by dp/dom/geo (rg: only dropword.js itself); only the `fwCount` event/ledger note remains pipeline.js:580-587. The *legacy* window (`windowWords`) is the actually-rendered analogue legacy.js:3016-3021.
12. **Heading text for TOC re-derived from layout.** `b.lines.map(l => l.words.join(' ')).join(' ')` pipeline.js:700, 888 — original raw heading text is dropped in favor of the line-broken reconstruction (legacy uses `t.text` directly legacy.js:3117).
13. **Editorial spans `##…##` deleted** by design (recorded to audit only) block-tokenizer.js:93-98.
14. **Legacy result strips tokens**: `tokensOut = {id:'lt'+t.id, type, level, text, num}` — `sideNote/endNote/syntheticTail` are not passed to the result contract legacy.js:3466.
15. **Quote normalization is one-way** (`״→׳`, `‘ ’→"`) block-tokenizer.js:13-18, and `U+FF9F/U+FF93` are mapped back to gershayim only inside accounting pipeline.js:902-903 — original characters unrecoverable.
16. **Legacy endnote tokens lose inline linkage**: endnote pages rebuild markers positionally (ni+1) legacy.js:3300, independent of any body anchor (endnotes mode has no body anchor by design — accounting counts marker+text at display pipeline.js:988-989).
17. **DP footnote split/move**: `text` is re-joined/sliced by word counts dp.js:272-275 — the continuation piece carries `continuationOf: n.tokenId` but not `noteIndex`, so a second split cannot be traced to the original noteIndex (only tokenId).
18. **Accounting blind spots (by design but relevant):** TOC rows, folios, headers, `(המשך)` labels, and shaar content are excluded/one-sided in both accountings (pipeline.js:960-996 note 2-4; legacy.js:3568 comment "תוכן-העניינים והפוליו לא נספרים"); legacy `meta.year` excluded legacy.js:3514.

## 4. Competing-model pairs (summary)

1. **Token models:** block-tokenizer tokens (typed, parts/notes) vs legacy `tokenizeDoc` tokens (`h0..h7`/`p`, sideNote/endNote strings) — two parsers, two shapes, one shared input text.
2. **Line-breakers:** `kp-linebreak.breakLines` (DP, boxes/glues/penalties) vs `LineBreaker.breakPara` (legacy greedy + first-word window + paren pitches) — plus *a third* internal greedy fallback inside KP itself kp-linebreak.js:199.
3. **Line models:** stacked `{words,widthPx,heightPx,isLast}+meta/seq` vs absolute `{words,markerIdx,paren*,y,paraId,lineIdx,align,sizePt,font}`.
4. **Page models:** dp `newPage`+spanning vs legacy `blankPageObj`+bands+gateLines+marginNotes. Cross-compat is shimmed defensively (dp.js:49-51 hash reads `p.sideNotes.length` on legacy pages; legacy.js:1140-1154 adds `sideNotes`+full `template` "חוזה התוצאה" for DP consumers).
5. **Footnote models:** DP `{text,marker,mode,heightPx}` (structurally linked to blocks) vs legacy queue/`fnQueue` string-keyed (`token#ordinal`) + two render forms (block `{marker,lines[{words,y}]}` vs continuous `{lines:[token[{t,mk,gap,noteIdx}]]}`).
6. **Marker authorities:** `notes/markers.markerFor` (DP + dom/geo fallbacks geo.js:392-398, dom.js:237) vs legacy `LineBreaker.markerWord(toGematria(num)+sep)` legacy.js:523 — markers.js:5-9 claims unification ("מקור־הסמכות היחיד") but the legacy path keeps its own converter.
7. **TOC models:** DP `toc-builder` (model rows → built pages inserted into `pages`, pipeline.js:708-727) vs legacy `makeTocPages`/`pg.toc` rows (legacy.js:3134-3259); plus a *third* "legacy compat" TOC built in the DP pipeline itself pipeline.js:874-892.
8. **Projectors:** `geometry-projector.projectPage` (DP) vs `legacy-projector` (placeWords legacy-projector.js:39-137) — both target the same pdf-writer/DOM contract but are separate implementations with separate font-key maps (geo.js:37-46 vs legacy-projector.js:142-150).
9. **Input hashes:** `contentHash(tokens)` block-tokenizer.js:135-144 (DP) vs legacy `contentHashIn` crypto-over-tokensOut legacy.js:3475-3481.
10. **Content accounting:** DP exact multiset equality + marker parity (pipeline.js:1010-1107) vs legacy ≥-coverage with different exclusions (legacy.js:3494-3589).

## 5. Next actions (for the unification plan)

- Introduce a structured word/run model (text + styleRefs + markerRef) to replace PUA-sentinel strings; the sentinel alphabet (E000/E101/E102/E103/E104) is the de-facto run encoding and is scrubbed irreversibly at render (dom.js:47).
- Unify the two footnote models around the DP structural one; the legacy string-keyed `token#ordinal` identity is the documented source of the duplicate/merged-note bugs (legacy.js:1447-1456, 2177-2184).
- Make marker↔note linkage structural end-to-end (replace regex renumbering markers.js:147-167 and tag-scan accounting pipeline.js:1041-1058).
- Decide the fate of dead fields `blk.dh` (pipeline.js:387) and `block.firstWord` (dropword.js:69) before merging models.
- Pick one line model (stacked vs absolute-y) and one page model; the shims at dp.js:49-51 and legacy.js:1140-1154 show the current contract friction.
